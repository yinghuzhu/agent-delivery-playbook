# 测试与验收

先读取目标项目规则、既有测试用例与运行说明，确认测试对象、环境、改动范围和用户授权。遵循用户选定的浏览器、缓存和数据保留要求。

## 角色与进入条件

- 用例设计阶段由用户与主 agent 共同完成；设计和用例同版确认、实施获授权后才能进入相应开发。只要求用例设计时不擅自开始实现或业务测试。
- 完整需求交付中的测试 agent 必须不同于开发 agent，在主 agent Review 通过后接收待测版本与必跑清单。开发单元测试和自测不能替代独立测试；工具不支持独立执行者时报告限制，不能自行降级或虚构身份。
- 测试 agent 只执行、举证、记录和复验，不修业务代码、不更改业务预期或降低断言以获得通过。用户仅要求单次只读测试时按该范围执行，不强制补齐整个开发流程。

## 默认采用定向验证

默认只验证本次变更功能、bug 原失败场景和有调用链／共享数据／接口契约／状态流转依据的受影响功能；不执行全系统全量回归。全量回归由 daily build 承担，只有用户明确要求全量，或当前任务明确为 daily build 全量验证时才执行。已有全量报告仅作参考，不能替代本次定向执行结果。

派工前由主 agent 核定用例白名单、选择原因、层级及定向执行命令。使用测试文件、用例 ID、模块或测试运行器过滤参数缩小执行范围；先核对命令含义，不直接运行会触发全仓库测试的默认命令。环境准备所必需的构建不代表授权执行全量测试。运行器不能过滤时先调查可拆分方式，确需执行全量则说明限制并请用户确认，不擅自扩大。

“系统用例检索”是覆盖与影响分析，不是要求执行全部检索到的用例；“所有必跑项”仅指本轮白名单。每轮修复复验原失败项和修复新增影响项；同版同环境已通过的无影响项复用已有证据，不重复跑。发现新增影响时补充具体关联用例并记录依据，不因一次失败升级全系统回归；影响不明先调查，确需全量交用户确认。

页面端到端验证也限定到本次及关联业务链路，不遍历无关页面或所有导航。复用 QA 工具时使用定向模式，避免工具默认探索范围扩大全系统测试。

## 用例整合与影响分析（执行前完成）

1. 记录待测代码基线、相关未提交改动和需求版本。读取系统测试文档、相关模块用例及自动化测试实现，不能只确认文件或测试类存在。
2. 在本需求唯一的用例文件中整理新增/修改场景与人工步骤；旧用例引用原文件路径和稳定编号，不复制成第二份。保留自动化测试原有模块结构；命令及结果仍分别存放。
3. 对照前置条件、输入、操作、预期，建立覆盖映射：需求/受影响行为 → 用例路径与编号 → 复用/修改/新增/废弃 → 原因。相同编号不证明语义一致，不同编号也可能重复；不同测试层级的有效覆盖不应误删。
4. 发现冲突时提交主 agent 核对已确认需求和当前完整调用链。主 agent 在设计阶段修订有依据的旧预期并保留编号追溯；业务口径不明或预期改变需用户裁决，测试执行者不得自行选择一套预期。合并完成后更新原入口及交叉链接，避免留下两套权威用例。
5. 从改动入口追踪调用方、共享方法、数据读写和状态推进，列出受影响旧功能及必跑用例。重点检查默认行为、旧数据/旧客户端兼容、提交与退回、异步回调等实际涉及的路径，不机械套用无关场景。
6. 形成可交接的必跑清单：用例路径/编号、覆盖原因、环境与数据前提、执行负责人。准备可获得的测试数据；账号或权限缺失明确列为阻塞，不让执行者猜测。用例写清具体输入、操作及可观察预期，不能用“结果正常”或引用不存在的部署/回退方案制造覆盖。

## 页面端到端验证与浏览器会话

- 涉及页面或用户交互的实施验收，必须通过实际浏览器操作已部署的待测版本，按确认用例执行完整业务流程，核对页面、请求及适用的持久化与关联汇总结果；不得以单测、接口成功或静态截图代替交互验收。纯接口、CLI 等无页面任务按适用层级验证，不强行引入浏览器。
- 默认复用现有环境、原会话和适用数据，在测试安排中说明复用范围及可选隔离；用户不需要隔离时直接复用，已有选择不重复询问。登录续期、缓存、历史状态和升级兼容等场景保留原标签页及状态。用例确需不同身份、干净初始状态或存在具体复用冲突时，说明受影响项和最小调整并与用户确认，不自动创建隔离环境或从头构造整套数据。独立测试 agent 的角色分工不等于独立环境或浏览器会话。
- 用例明确浏览器入口、账号角色、登录状态、Cookie／LocalStorage／SessionStorage／缓存、已有数据及刷新或重启等必要操作。影响结果的前置条件不明确时由主 agent 补齐确认；不得通过清缓存、重新登录或新建会话绕过原场景。状态重置仅按用例或用户明确要求执行，保留重置前结果。
- 报告记录会话选择、前置状态、待测版本、实际步骤和预期对比，并提供脱敏截图、请求或数据证据。浏览器工具不可用、原会话无法访问、账号或前置条件缺失时将依赖用例标记 BLOCKED，说明原因并继续可独立执行项，不宣称端到端通过。

## 数据复用与并行执行

先核对现有数据能否满足确认用例，记录必要基准，仅在授权范围补充实际缺口；不因未隔离而拒绝测试。用户不选择隔离时，可顺序执行、错峰或使用其他已有合适记录；仍缺必要条件的用例如实阻塞，不降低断言。环境复用不代表可以任意修改或清理已有业务数据。

主 agent 按用例核对前置依赖、Page/登录状态、数据读写、共享库存/额度/汇总、全局配置、后台任务、清理和待测版本等实际资源。无冲突且有收益的组可并行，存在依赖的步骤保持顺序；不同页面、账号或数据 ID 不能直接证明无冲突。关系未明先补查或串行，不为并行强制隔离；专门验证竞争条件的用例仍按确认时序执行。

测试任务单记录用例编号、资源和冲突判断、并行组/串行顺序、执行者及证据位置。各测试 agent 独立于开发，遵守已有模型与预算选择，各自独占 Page；按浏览器规则分配空间和协调共享动作，由主 agent 统一管理共享空间结束。清理不能影响其他组，发现干扰即暂停受影响项、保留证据并交主 agent 重排和核定复验；不把受污染结果计为通过。

## 工作流程

1. 从需求和实际实现形成场景矩阵，优先覆盖本次变化的正常、边界、失败和受影响旧流程；涉及权限、租户、重复请求或事务时覆盖相应隔离与一致性。
2. 区分预期与实现：金额、数量和状态依据业务规则独立推导预期值，不能直接复用被测算法作为断言。
3. 核对开发回传的单元测试/自测及主 agent Review 记录；单元测试 Mock 所有外部服务，数据库集成测试使用隔离环境，MySQL 使用 Testcontainers。页面与业务验收默认复用现有环境和数据，浏览器验证实际部署产物，记录版本与入口。开发不得并发改变受测用例依赖的工作区/产物/配置/数据前提；其他无冲突开发活动可继续。此处页面验收的复用约定不改变自动化数据库集成测试的环境要求。
4. 按风险执行相关层级。涉及代理或入口差异时分别验证直连与代理；涉及页面初始化时验证列表进入、深链和刷新。用户要求保留缓存时不得清缓存绕过问题。
5. 对业务链路核对页面输入、请求响应、数据库持久化、关联列表及汇总；例如采购新增后应付款同步可见，金额符合业务口径。
6. 失败时保存最小复现与证据，区分业务缺陷、环境/夹具问题和待裁决歧义。普通问题完成一轮后汇总给主 agent 与开发确认；阻断或污染立即报告，并继续独立可执行的用例。开发可提供反证，但不能单方否决测试证据。
7. 开发修复经主 agent Review 后，测试 agent 复验原失败用例和受影响旧功能，主 agent 核验结果后关闭问题。复验失败继续循环；业务歧义交用户裁决，不以改预期替代修复。
8. 实际执行必跑清单中的新增、修改和复用旧用例，报告本轮范围内的通过、失败、未执行、阻塞；主 agent 核验逐项证据，不能仅凭“测试已完成”的总结。所有产物包括报告未经本次批准不得提交 Git；本 skill 不授权外部消息或生产操作。

每轮固定设计/用例、源码与制品版本。源码未提交时记录 HEAD＋完整差异和相关文件哈希（含未跟踪文件），无 Git 基线则记录文件清单与哈希，不为测试创建临时提交。源码、配置、数据前提或制品改变后由主 agent 重新核定 Review 和复测范围；不能混用旧报告证明新版本通过。

## 输出约定

沿用项目目录与格式，无约定时分开输出：
- 用例：编号、需求/缺陷关联、前置条件、测试数据、操作步骤、预期结果、清理条件。仅含可重复执行的用例。
- 运行说明：环境准备和测试命令。
- 执行报告：轮次、设计/用例版本、环境/源码/制品、执行时间、执行人、用例路径/编号及结果、实际观察与证据、缺陷编号、恢复情况、未执行/阻塞原因、人工验收入口。

测试数据只在授权环境创建和清理，不删除已有业务数据。证据中隐藏凭据与敏感信息。

## 完成标准

测试设计交付与执行验收分开：只要求设计时，完成覆盖映射和必跑清单，明确尚未执行。实施验收时，本轮白名单中的所有必跑项必须有实际执行结果；缺少结果的标记未执行或阻塞，不得宣布全部验收完成。检查类名存在、文档链接或静态格式不等于执行测试。

所有必跑项实际通过、必须修复的问题复验关闭且文档一致时，由主 agent 报告“待人工验收”，最终验收由用户确认。延期或不修需用户裁决并单列，不能计为通过。只通过单元测试时明确其边界，不宣称整个业务验收通过。
